# dovetail on DuckDB 2.0, FineType v0.6.64: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** dovetail links DuckDB 2.0.0 through the `duckdb` crate `=1.20000.0` and pins FineType to v0.6.64, with every test passing and survey's and relate's outputs unchanged except where a named upstream change moves them.

**Architecture:** Two dependency moves, each its own commit with its own output comparison against `main`: first the DuckDB engine, then the FineType tag. No dovetail logic changes unless a test shows DuckDB 2.0 or FineType 0.6.64 requires one.

**Tech Stack:** Rust workspace; `duckdb` crate, bundled; `finetype-core` and `finetype-model` as git dependencies on a tag.

**Spec:** `docs/superpowers/specs/2026-10-26-duckdb-2-design.md`

## Global Constraints

- `duckdb = { version = "=1.20000.0", features = ["bundled"] }`, the same spec as Brightfield's.
- `finetype-core` and `finetype-model` both at `tag = "v0.6.64"`. `Cargo.lock` must record commit `5c0dd5559607cc90747e0871913bc6318511cabd` for both.
- `SELECT version()` on a dovetail connection returns exactly `v2.0.0`.
- One cargo build at a time on the development Mac. A cold bundled-DuckDB build takes about 10–15 minutes there.
- Commit `Cargo.toml` and `Cargo.lock` together. Never `git add -A`.
- Public repo: no issue-tracker refs or local paths in commits, the PR or tracked files.

## Review Focus

1. A `CXXFLAGS` already set in the shell overrides `.cargo/config.toml`'s, and the build then names itself `v2.0.0-dev88614`. Task 1's version test catches this; a reviewer should not treat a failure there as flaky.
2. A model directory without `validation_snapshot.json` makes survey's model-backed eval read 0.6.64's new rules rather than the frozen ones, and the results move for a reason that is not the pin. Task 2 checks the file is present before running the eval.
3. Uppercase UUID and 32-hex columns in the fixtures change type under 0.6.64. A changed field type in survey's descriptor is expected only for those; any other changed field is a finding.
4. DuckDB 2.0 plans `count(*)` from statistics and runs a query that has several `DISTINCT` aggregates over a CTE. relate's overlap and cardinality numbers must not move. If one does, find the cause; do not re-record it.
5. The release extension loads only under the file name `finetype.duckdb_extension`. Task 2's test copies it to that name rather than loading the release's own file name.

### Task 1: Move the DuckDB engine to 2.0.0

**Files:**

- Create: `.cargo/config.toml`
- Modify: `Cargo.toml` (add `[profile.dev.package.libduckdb-sys]`)
- Create: `crates/dovetail-core/tests/duckdb_engine.rs`
- Modify: `Cargo.lock`

**Interfaces:**
- Produces: `tests/duckdb_engine.rs`, which Task 2 extends.

- [ ] **Step 1: Record `main`'s outputs.** Before any change, build the CLI on this branch (still `main`'s code) with `cargo build -p dovetail`, then run the comparison script, `cmp-outputs.sh <out-dir>`, which you write in the session's scratch directory and do not track. It copies each of `tests/fixtures/*/` to a temporary directory, runs `target/debug/dovetail survey` on its data file, and keeps stdout plus every file survey wrote. It also builds a database from `tests/relate-fixtures/build.sql` and from `identifier-keys.build.sql` with the DuckDB 2.0 CLI, attaching each file with `(STORAGE_VERSION 'v1.4.0')` so DuckDB 1.5 can read it, and runs `dovetail relate <db> --out <dir>/relate.json` on each. Save the result to `<scratch>/baseline-main`. Expected: one output directory per fixture, and no errors.
- [ ] **Step 2: Write the failing test.** In `tests/duckdb_engine.rs`, `the_bundled_duckdb_is_2_0_0`: open `duckdb::Connection::open_in_memory()`, query `SELECT version()`, assert it equals `"v2.0.0"`. The failure message should say that a shell `CXXFLAGS` overrides `.cargo/config.toml`.
- [ ] **Step 3: Run it.** `cargo test -p dovetail-core --no-default-features --test duckdb_engine`. Expected: FAIL, reporting `v1.5.x`.
- [ ] **Step 4: Move the pin.** Set the `duckdb` line in `crates/dovetail-core/Cargo.toml` to the spec in Global Constraints. Create `.cargo/config.toml` with `[env] CXXFLAGS = '-DDUCKDB_VERSION="v2.0.0"'`, and a comment giving the reason (duckdb/duckdb-rs#917: libduckdb-sys 1.20000.0 compiles DuckDB 2.0.0 as `v2.0.0-dev88614`, and that build fetches extensions from a path nothing is published under) and saying the entry goes once a libduckdb-sys release carries the fix. Add `[profile.dev.package.libduckdb-sys] debug = false` to the root `Cargo.toml`, with a comment that from 1.20000.0 debug info turns on DuckDB's `DEBUG` verification paths and makes each test binary about a quarter larger. Then run `cargo metadata --format-version 1 >/dev/null`.
- [ ] **Step 5: Run the test.** Same command as Step 3. Expected: PASS.
- [ ] **Step 6: Audit dovetail's SQL for 2.0 changes.** Search the SQL strings in `crates/dovetail-core/src` and `tests/` for the constructs whose results change in DuckDB 2.0: `~` and `!~`, `//` and `%` where the divisor can be zero, `x -> …` lambdas, and `ORDER BY true`. Also check the 2.0 migration guide's PEG-parser notes against any SQL dovetail emits. Fix only what the guide says behaves differently, and list each fix, or "none", for the PR.
- [ ] **Step 7: Run the gate.** `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, then `cargo clippy --workspace --all-targets --no-default-features -- -D warnings` and `cargo test --workspace --no-default-features`. Expected: all pass. A test that fails here and also fails on `main` is a ruling: record it and raise its fix separately.
- [ ] **Step 8: Compare outputs.** Rebuild the CLI, run `cmp-outputs.sh <scratch>/after-duckdb`, then `diff -r <scratch>/baseline-main <scratch>/after-duckdb`. Expected: no differences, other than a DuckDB version string that survey's provenance stamp carries, if it carries one. Name every other difference in the commit message, with its cause.
- [ ] **Step 9: Commit.** `git add .cargo/config.toml Cargo.toml Cargo.lock crates/dovetail-core/Cargo.toml crates/dovetail-core/tests/duckdb_engine.rs` plus any file Step 6 fixed. Message: "Move to DuckDB 2.0.0 through duckdb 1.20000.0, naming the bundled build v2.0.0". Wait for roborev's review of the commit (`roborev wait <sha>`) and fix its findings before Task 2.

### Task 2: Pin FineType to v0.6.64

**Files:**
- Modify: `Cargo.toml` (both `tag`s, and the comment above them)
- Modify: `Cargo.lock`
- Modify: `crates/dovetail-core/tests/duckdb_engine.rs`
- Modify: any test whose expected value moves under 0.6.64

**Interfaces:**
- Consumes: `tests/duckdb_engine.rs` from Task 1.

- [ ] **Step 1: Write the test.** In `tests/duckdb_engine.rs`, add `the_release_extension_reports_the_pinned_version`. It skips, printing why, unless `DOVETAIL_FINETYPE_EXTENSION` names an existing file. Otherwise it reads the `finetype-core` tag out of the workspace `Cargo.toml` (`include_str!("../../../Cargo.toml")`), copies the extension to `finetype.duckdb_extension` in a temporary directory, opens a connection with `duckdb::Config::default().allow_unsigned_extensions()`, runs `LOAD '<copy>'`, and asserts `SELECT ft_version()` equals `"finetype "` followed by the tag without its leading `v`.
- [ ] **Step 2: Run it against the v0.6.64 extension while the pin is still v0.6.60.** Download it: `gh release download v0.6.64 -R meridian-online/finetype -D <scratch>/ft -p 'finetype-v0.6.64-aarch64-apple-darwin.duckdb_extension*'`, and check it with `shasum -a 256 -c` against the `.sha256` file. Then `DOVETAIL_FINETYPE_EXTENSION=<scratch>/ft/finetype-v0.6.64-aarch64-apple-darwin.duckdb_extension cargo test -p dovetail-core --no-default-features --test duckdb_engine`. Expected: FAIL, expected `finetype 0.6.60`, found `finetype 0.6.64`.
- [ ] **Step 3: Move the tag.** Set `tag = "v0.6.64"` on `finetype-core` and `finetype-model` in the root `Cargo.toml` and update the comment's version. Run `cargo metadata --format-version 1 >/dev/null`, then `awk '/^name = "finetype-core"/{f=1} f && /^source = /{print; exit}' Cargo.lock`. Expected: the source ends `#5c0dd5559607cc90747e0871913bc6318511cabd`.
- [ ] **Step 4: Run the test.** Same command as Step 2. Expected: PASS. Without the variable set, it reports a skip.
- [ ] **Step 5: Fetch the model for the eval.** In a scratch directory, run FineType v0.6.64's `.github/scripts/download-model.sh` (taken with `git show v0.6.64:.github/scripts/download-model.sh` from a FineType clone) with `FINETYPE_CI_MODEL=m2v8m-s43`, the model the v0.6.64 release's `finetype-model.json` names. Check `models/m2v8m-s43/validation_snapshot.json` exists. If the download did not fetch it, copy it from the tag (`git show v0.6.64:models/m2v8m-s43/validation_snapshot.json`) and say so in the PR.
- [ ] **Step 6: Run the gate, model-backed and floor.** Run the five commands from Task 1 Step 7. Then run `DOVETAIL_FINETYPE_MODEL_DIR=<scratch>/models/m2v8m-s43 cargo test -p dovetail-core --test eval_harness -- --nocapture` and keep `target/eval-results.md`. Expected: all pass. For each expected value that fails, check that a 0.6.64 change explains it (CHANGELOG 0.6.64: UUID case, `tsid`, `percentage`, `file_size`, `currency_code` and the others listed there). If one does, re-record the value and note the type. If none does, it is a finding: investigate it, do not re-record.
- [ ] **Step 7: Compare outputs.** Run `cmp-outputs.sh <scratch>/after-finetype` twice, once with `DOVETAIL_FINETYPE_MODEL_DIR` unset and once with it set, and diff each against `<scratch>/after-duckdb`. Run the same two passes on `main`'s build from Task 1 Step 1 if you need a model-backed baseline. Name every changed field, with its file, old type, new type and the 0.6.64 change that explains it.
- [ ] **Step 8: Commit.** `git add Cargo.toml Cargo.lock crates/dovetail-core/tests/duckdb_engine.rs` plus any re-recorded test. Message: "Pin FineType to v0.6.64, whose extension dovetail will load", and in the body, the changed fields from Step 7 and the eval's model-backed hit rate before and after. Wait for roborev's review (`roborev wait <sha>`) and fix its findings.
